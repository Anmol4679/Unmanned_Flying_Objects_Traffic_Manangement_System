1. EXECUTIVE SUMMARY & ARCHITECTURE OVERVIEW
===============================================================================
The Unmanned Flying Objects Traffic Management System (UTM) is an enterprise-grade
distributed platform designed for civil aviation authorities, fleet operators,
and dispatchers to manage low-altitude airspace safely and deterministically.

Key Architectural Characteristics:
- Backend: FastAPI (Python 3.11+ / ASGI), SQLAlchemy 2.0 ORM, psycopg3,
  SlowAPI rate limiting, python-jose (JWT), passlib with bcrypt hashing,
  resilient 2-second fallback to SQLite (`utm_drone.db`) if PostgreSQL is offline.
- Caching & Real-Time Ingestion: Redis 7 (in-memory key-value hash cache) for
  ultra-low latency drone telemetry storage and retrieval.
- Real-Time Messaging: Full-duplex WebSockets (`/ws/telemetry`) with client pool
  connection management for instantaneous telemetry broadcasting to flight radar clients.
- Database: PostgreSQL (`utm_drone_db`) with raw SQL spatial extensions, GiST bounding
  box indexes, B+Tree temporal indexing, and Alembic database migrations.
- Frontend: React 19 + TypeScript + Vite, Tailwind CSS, Lucide React icons,
  React Router DOM v7, Custom Auth & RBAC Route Guard System.
- Concurrency Engine: Pessimistic locking (`SELECT ... FOR UPDATE`) preventing
  airspace sector overbooking, accompanied by an automated emergency preemption pipeline.
- Production Containerization: Multi-stage Dockerfiles for backend and frontend,
  Nginx reverse proxy with WebSocket upgrade support, and full multi-container
  orchestration via `docker-compose.yml`.
- CI/CD Automation: GitHub Actions workflow (`.github/workflows/ci.yml`) validating
  test suites and code quality on every push and pull request.
- Test Coverage: 27 / 27 unit, integration, concurrency, and WebSocket tests passing.

4.1. MODULE 1: IDENTITY, AUTHENTICATION & RBAC
--------------------------------------------------------------------------------
Primary Author: Anmol Saluja (Anmol4679)
Additional Hardening: Shravan2307 (Direct bcrypt, demo accounts, auth resilience)
Backend Files:
  - backend/modules/identity/models.py
  - backend/modules/identity/schemas.py

Frontend Files:
  - frontend/src/shared/context/AuthContext.tsx

  - frontend/src/shared/components/RequireRole.tsx
  - frontend/src/shared/components/Forbidden403.tsx
  - frontend/src/shared/types/auth.ts

Key Features & Specifications:
- Data Models:
  * `operator` (`Operator` model): `operator_id` (PK, INTEGER), `name` (VARCHAR(100)),
    `license_no` (VARCHAR(30), UNIQUE), `role` (VARCHAR(20), CHECK: 'FLEET_OPERATOR',
    'REGULATOR', 'DISPATCHER'), `password_hash` (TEXT).
  * `audit_log` (`AuditLog` model): `id` (PK, BIGINT), `actor_id` (INTEGER, nullable, no FK
    to ensure audit retention), `action` (TEXT), `entity` (TEXT), `entity_id` (INTEGER, nullable),
    `created_at` (TIMESTAMP).
- Security Architecture:
  * Password Hashing: Direct bcrypt hashing with 72-byte safe truncation (mitigating
    Python 3.14 passlib compatibility deprecations).
  * Token Format: JWT (HMAC-SHA256) containing `id` (int), `operator_id` (int), `role` (str),
    `sub` (str, license_no), and `exp` (timestamp expiry).
  * Rate Limiting: SlowAPI memory limiter on `/api/auth/login` configurable via
    `LOGIN_RATE_LIMIT` environment variable (defaults to "5/minute").
  * RBAC Enforcers: `require_role(["REGULATOR", ...])` FastAPI dependency.
  * Demo Seeding: Automatic on-startup seeding of demo accounts (LIC-FLEET-001,
    LIC-REG-001, LIC-DISP-001) with 1-click login buttons in the frontend UI.
- Endpoints:
  * POST /api/auth/register - Register a new operator (default role FLEET_OPERATOR).
  * POST /api/auth/login - Authenticate credentials and issue JWT access token.
  * GET  /api/operators/me - Retrieve profile information of the authenticated operator.
  * GET  /api/operators - List all operators (Restricted to REGULATOR role).
  * PATCH /api/operators/{id}/suspend - Suspend/unsuspend operator account (REGULATOR only).
  * GET  /api/audit-log - View compliance and security audit logs (REGULATOR only).

    FK -> `drone.drone_id` ON DELETE CASCADE), `priority_clearance_level` (INTEGER).

  * Atomic creation & editing: Drone base record and corresponding subtype record created/updated
    within a single ACID transaction; rolls back completely on any validation error.

  * PATCH /api/drones/{id}/status - Update drone operational status.

  - backend/tests/concurrency_test.py
  - backend/tests/test_reservations.py
Frontend Files:
  - frontend/src/reservations/components/EmergencyPreemption.tsx

Key Features & Specifications:
- Pessimistic Concurrency Locking:
  * Time slots are fetched using `db.query(TimeSlot).filter(...).with_for_update().first()`.
  * Locks the specific time slot row at PostgreSQL engine level until transaction commit.
  * Guaranteed prevention of overbooking even under 100+ simultaneous requests.
- Emergency Preemption Corridor Engine:
  * When a reservation is marked as `EMERGENCY` (e.g. medical transport or organ delivery),
    the system checks if capacity is exceeded.
  * If the slot is full, the engine preempts the most recently booked `ROUTINE` reservation:
    - Sets existing reservation status to `PREEMPTED`.
    - Decrements current booking count and re-allocates slot to the emergency flight.
    - Creates an automated audit trail entry recording the preemption event.
- Endpoints:
  * POST /api/reservations/emergency-preemption - Request emergency flight corridor override.
- Automated Concurrency Testing:
  * `concurrency_test.py`: Runs 20 concurrent asynchronous workers competing for 5 slot
    spots; asserts exactly 5 succeed and 15 receive 409 Conflict without data corruption.

    the specified UAV.
  * WS `/ws/telemetry` - Full-duplex WebSocket connection handling real-time stream broadcast
    to active operator dashboards and flight radar clients.

    of disconnected or stalled sockets during broadcast cycles.
- Automated Testing & Scripting:
